# 부모 계정 도입 설계안

상태: **1단계 코드 구현 완료, 기능은 꺼져 있다(2026-11-19). Supabase 프로젝트는 아직 없다.**
사용자 방침(2026-10-22): 계정과 개인정보 처리는 **성인인 부모**를 대상으로 한다. 2026-11-19 사용자가 구현 시작을 알렸다.

### 구현 현황과 켜는 방법

| 항목 | 상태 |
|---|---|
| 스키마·RLS·권한·저장/삭제 함수 | `supabase/migrations/0001_parent_accounts.sql`. 권한(grant)을 직접 준다 — 새 Supabase 프로젝트는 표·함수에 자동 권한을 주지 않는다. 임시 Postgres에서 `npm run test:db`로 검증(자동 권한이 있는 프로젝트·없는 프로젝트 두 경우, 정책·권한을 풀면 실패하는 것까지 확인). 실제 프로젝트에는 아직 적용 안 함 |
| 로그인 | 이메일 6자리 코드**만**, 비밀번호 없음. 메일 속 링크 로그인은 쓰지 않는다(다른 브라우저에서 열려 이어지지 않고, 동의 기록 단계를 건너뛰며, 주소에 로그인 정보가 남는다). 코드를 보러 메일 앱에 다녀와도 코드 입력 단계가 유지된다. `src/lib/account.js`, `src/screens/AccountPanel.jsx` |
| 동의 | 이용약관·개인정보·국외전달 3건을 버전(`CONSENT_VERSION`)과 함께 기록. 문구는 **초안**(`src/lib/consentText.js`), 법률 검토 전 |
| 저장/불러오기 | 아이 프로필·별·콜렉션만 계정에 올린다(대화·안전 알림·PIN은 올리지 않음). 낙관적 잠금(`rev`)으로 다른 기기 덮어쓰기 방지. **수동**(버튼) — 자동 저장은 아직 |
| 삭제 | 부모 화면에서 계정과 모든 데이터 삭제(`delete_my_account`) |
| 화면 | 부모 화면의 "부모 계정" 카드. 서버에 설정이 없으면 보이지 않음 |

**켜는 순서(사용자 작업 포함):**
1. Supabase 프로젝트를 만든다(이 세션에서는 생성 권한이 거부돼 만들지 못했다. 대시보드에서 직접 만들거나, 허용하면 이어서 한다). 지역은 서울(`ap-northeast-2`)을 권장.
2. `supabase/migrations/0001_parent_accounts.sql`을 적용한다(SQL Editor에 붙여넣기, 또는 이 세션이 `apply_migration`으로 적용).
3. Render `childhood` 서비스 환경변수 두 개를 추가한다 — 둘 다 공개 값이다: `SUPABASE_URL`(`https://<ref>.supabase.co`), `SUPABASE_PUBLISHABLE_KEY`(`sb_publishable_…`). **비밀 키(service_role / sb_secret_)는 넣지 않는다** — 서버가 거부한다.
4. Supabase 대시보드 Authentication › Email Templates의 **"Magic Link"와 "Confirm signup" 두 템플릿 모두**에서 링크(`{{ .ConfirmationURL }}`)를 빼고 `{{ .Token }}`(6자리 코드)만 넣는다. 기본 템플릿은 링크만 있어 그대로 두면 로그인할 수 없다. (처음 가입하는 주소에는 "Confirm signup" 템플릿이 쓰일 수 있다 — 6번에서 새 주소로 실제 확인한다.)
5. **메일 발송:** Supabase 기본 메일은 테스트용이라 프로젝트 조직 구성원 주소로만 보내고 시간당 건수도 아주 적다. 실제 테스터 부모에게 코드를 보내려면 커스텀 SMTP(예: Resend)가 필요하고, 그러려면 **발신 도메인 인증(도메인 구매)** 이 먼저다.
6. 실제 메일로 가입→저장→다른 브라우저에서 불러오기를 사람이 한 번 확인한다(자동 테스트는 가짜 Supabase를 쓰므로 메일 수신은 확인하지 못한다).

**2026-11-19 코드 리뷰에서 고친 것:** 마이그레이션에 권한 부여 누락(새 프로젝트에서는 모든 요청이 42501로 실패했을 것), 휴대폰에서 메일 앱에 다녀오면 로그인 단계가 사라지던 것, 충돌 뒤 "불러오기"가 화면의 옛 기록을 쓰던 것, 불러오기 때 이 기기에만 있는 아이가 말없이 사라지던 것(이제 이름을 알린다), 링크 로그인(동의 누락) 제거, 동의 기록 수 상한(60), 크기 제한을 바이트 기준으로 통일, 오류 안내 분류, 터치 영역.

**알려진 한계(1단계):** 새 기기에서 불러오려면 먼저 가입(아이 프로필·PIN 만들기)을 한 번 거쳐 부모 화면에 들어가야 한다. 불러오면 그 임시 프로필은 계정의 아이들로 바뀐다. 가입 화면의 "이미 계정이 있어요" 입구는 다음 단계에서 만든다. 불러오기는 오늘의 진행(미션·횟수)도 저장 시점 값으로 되돌린다(부모 PIN 뒤에서만 가능).

**다음 단계(미구현):** 자동 저장, 서버가 로그인 토큰을 검증하는 `/api/chat`과 계정 단위 하루 한도, PIN 서버 검증·이메일 재설정, 안전 알림·사용 현황 서버 저장(2~3단계).

법률 판단은 이 문서에 없다. 개인정보 처리방침·동의 문구는 전문가 확인을 거친다.

## 1. 왜 필요한가 (지금의 한계)

| 문제 | 지금 | 계정이 있으면 |
|---|---|---|
| 기기를 바꾸거나 브라우저 데이터를 지우면 별·콜렉션·프로필이 사라짐 | 데이터가 기기 localStorage에만 있음 | 부모 계정에 저장되어 복구됨 |
| 부모 PIN을 아이가 재설정할 수 있음 | "PIN 잊음" = 계산 문제 하나 | 재설정을 **부모 이메일 링크**로 하게 되어 아이가 못 함 |
| 하루 사용 한도를 새 프로필로 피할 수 있음(PIN 있을 때만 막음) | 한도가 기기·프로필 단위 | 한도를 **계정 단위**로 서버에서 셈 |
| 요청 제한이 IP 기준이라 한 명이 전체 상한(300/일)을 소진할 수 있음 | IP별·전체 상한 | 계정별 상한 + 로그인한 사용자만 채팅 |
| 보호자 동의의 근거가 없음 | 동의 절차 없음 | 가입 때 부모가 동의하고 버전·시각이 기록됨 |

## 2. 추천안 (한눈에)

- **로그인:** 부모 **이메일 링크(비밀번호 없음)**. 이후 카카오 로그인 추가를 검토한다.
- **저장소:** **Supabase**(Auth + Postgres + 행 단위 보안). 이 세션에 Supabase 연동이 붙어 있어 프로젝트 생성·마이그레이션을 이어서 할 수 있다.
- **메일 발송:** Resend(연동 있음) 또는 Supabase 기본 메일. 무료 한도는 도입 전에 확인한다.
- **채팅 내용의 서버 저장:** **기본은 저장하지 않는다**(기기에만 둔다). 부모가 볼 "사용 현황"과 "안전 알림"만 서버에 둔다. (결정 필요: 아래 6번)
- **기존 데이터:** 첫 로그인 때 기기의 `banjjaktalk_v2` 데이터를 계정으로 한 번 가져온다. 저장 키는 바꾸지 않는다.

## 3. 데이터 모델 (초안)

```
parents        (id = auth.users.id, email, created_at, deleted_at)
consents       (parent_id, document, version, accepted_at)        -- 약관 / 개인정보 / 국외이전 고지
kids           (id, parent_id, name, birth_year, birth_month, avatar, interests, plan)
kid_state      (kid_id, rewards jsonb, decor jsonb, badges jsonb, stickers jsonb, updated_at)
settings       (parent_id, limit_per_day, pin_hash, pin_fails, pin_locked_until, voice, sound)
usage_daily    (kid_id, day, messages)                            -- 하루 한도를 서버가 셈
safety_events  (id, kid_id, at, category, activity_id, excerpt)    -- 부모 안전 알림용. 보관기간 짧게
```

- 모든 표는 `parent_id`로 **행 단위 보안(RLS)** 을 걸어 부모 본인 행만 읽고 쓰게 한다.
- `safety_events.excerpt`는 아이가 한 말의 일부라 가장 민감하다. 길이를 제한하고 보관기간(예: 90일)을 정한다.
- PIN은 해시로만 저장하고, 시도 횟수 제한을 서버가 한다.

## 4. 서버(`server.js`) 변경

1. `/api/chat`은 **로그인 토큰을 검증**하고, 계정 단위 일일 한도를 적용한다(IP 한도는 보조로 유지).
2. 한도·안전 이벤트는 서버가 기록한다. 클라이언트가 보내는 값을 믿지 않는다.
3. 환경변수 추가: Supabase URL, 서비스 키(서버 전용). **키는 대화나 저장소에 적지 않고 Render 대시보드에만 넣는다.**
4. `/api/health`에 데이터베이스 연결 상태를 추가한다(값은 노출하지 않음).

| 단계 | 내용 | 끝났다고 볼 기준 |
|---|---|---|
| 0 | 개인정보 처리방침·약관·국외이전 고지 초안, 결정 사항(6번) 확정 | 사용자 승인 |

| 2 | 서버 검증(토큰), 계정 단위 한도, PIN 서버 검증·이메일 재설정 | 한도 우회·PIN 재설정 테스트 통과 |

## 6. 사용자가 정해야 할 것

1. **로그인 방식:** 이메일 링크만 / 이메일 + 카카오. (추천: 이메일 링크로 시작)
2. **채팅 내용을 서버에 저장할지:** 저장하지 않음(추천) / 부모가 볼 수 있게 저장. 저장하면 개인정보 처리 부담과 유출 시 영향이 커진다.
3. **보관기간:** 안전 알림 발췌, 비활성 계정, 삭제 요청 처리 기한.
4. **가입 연령:** "만 19세 이상 보호자"로 한정할지(약관 문구와 확인 절차).
5. **법률 검토를 맡길 곳**과 처리방침 문구의 책임자.
6. **서비스 지역:** 서버·DB 위치(Oregon 등 해외)와 이에 대한 고지 방식.

## 8. 위험과 대응

- **유출:** 저장 항목을 최소화하고(채팅 내용 미저장), RLS와 서비스 키 분리를 지킨다.
- **무료 플랜 한계:** Supabase·Render 무료 플랜의 정지·만료 정책을 도입 전에 확인한다. 아이 서비스가 멈추지 않도록 유료 전환 시점을 정한다.
- **로그인 장벽:** 가입이 번거로우면 이탈한다. 처음에는 계정 없이 쓰고 나중에 계정에 연결하는 흐름(기기 데이터 가져오기)을 유지한다.
- **구독:** 결제를 붙이면 결제 업체 선택·환불 정책이 추가된다. 이 설계안은 결제를 포함하지 않는다.
